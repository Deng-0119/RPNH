# Atomic tools executed by a typed Petri net

An offline, synthetic electricity-bill example. The two input documents contain
1,500 Wh at 80 fen/kWh and 500 Wh at 100 fen/kWh. The result is **2.000 kWh,
1.20 + 0.50 = 1.70 CNY**. Nothing contacts a utility, pays a bill or calls a model.

The point is the execution boundary: **ten individual operations are admitted
and settled by the existing Harness and the same Registry**. Each operation
invokes one exact registered HOST tool. Checkers, normalization, AND-join,
calculation, independent validation and final publication are actual transitions.
No Python function orchestrates the business steps.

## Run from the repository root

Use the repository's normal Python 3.11+ development environment with its core
and test dependencies installed. This is a source-checkout, trusted-HOST example;
it does not add or replace the installed `rpnh` session interface.

```bash
python -m examples.tool_pipeline.run \
  --run-dir /tmp/rpnh-tool-pipeline-run \
  --output-dir /tmp/rpnh-tool-pipeline-export
```

Both directories must be absent. The fixed inputs default to
[usage.json](fixtures/usage.json) and [tariff.json](fixtures/tariff.json).
`--usage FILE`, `--tariff FILE` and `--max-in-flight 1|2` are optional.
All accepted numeric input values are bounded, nonnegative integer **strings**;
no binary float conversion is involved. UTC intervals must be unique, ordered
in time without overlap, and match exactly across sources.

The launcher prints PASS only for Registry terminal evidence whose `run_outcome`
is `complete`. A rejected business input produces an explicit rejection resource
and no success terminal. When all admitted siblings drain, its finite run ends
with `quiescent_marking` and exit code 1. Rejections from both branches are
retained; there is no competing pair of failure-terminal bindings. Unexpected
worker errors leave unresolved firing evidence and do not become validation
success or an automatically replayed call.

Outputs are derived, disposable artifacts:

- `report.json`: the exact final resource, including source, candidate and
  validation version refs
- `evidence.json`: adopted definition, terminal evidence, all intermediate
  resources/provenance, firing records and ordered Registry events
- `adopted-pn.json` and `projection.json`: the actual compiled declaration and
  read-only Registry net projection

Rebuild exports without the original process or its Python objects:

```bash
python -m examples.tool_pipeline.run --readback \
  --run-dir /tmp/rpnh-tool-pipeline-run \
  --output-dir /tmp/rpnh-tool-pipeline-readback
rpnh net --run /tmp/rpnh-tool-pipeline-run --view
```

The custom application schemas are embedded in the adopted declaration. The
example readback explicitly supplies its schema catalog. Keep generated runs and
exports outside the repository; do not commit Registry databases.

## The explicit declaration

[module.json](module.json) is a fixed `ModuleDeclaration`, lowered through the
existing `operation` component into ten `PNFragment` transitions and 18 fused
places. It can be authored by a person or generated by an agent. Execution does
not depend on who authored it; this offline example uses zero model calls.

```text
usage source -> read_usage -> check_usage_input -> normalize_usage --+
                 |                                                  |
                 +-- usage_validation_source -------------------+   |
                                                                |   v
                                                            validate_report <- compute_cost <- join_intervals
                                                                ^                  |
                 +-- tariff_validation_source ------------------+                  |
                 |                                                                 |
tariff source -> read_tariff -> check_tariff_input -> normalize_tariff --------------+

validate_report --validated--> publish_report --final--> success terminal
check_* / join_intervals / validate_report --rejected--> rejection resource
```

The source copies used by the validator are **explicit second products** of each
read, with distinct Registry refs and consuming tokens. A consuming output is
never silently broadcast. `join_intervals` has two required typed inputs and
cannot start with only one normalization. `validate_report` consumes the candidate
and both original-source snapshots. `publish_report` requires the separately
registered validated resource; a candidate's JSON flag cannot enable it.

Every input has an exact `ResourceVersionRef`. Every output uses the existing
`PetriOutputOrigin`, output binding, schema authority, `derived_from` relation,
output registration and ordinary Success path. Business `parents` fields are
checked against actual delivered inputs before publication; they do not grant
read permission. Tools receive only their claimed input values/refs and the
frozen policy. They cannot dereference arbitrary same-name or same-Registry refs.

## Actual tool ABI, concurrency and trust

[host.py](host.py) explicitly registers one tool and one one-step executor per
transition. For example:

- Tool: `example/tool_pipeline/read_usage/v1`
- Executor: `example/tool_pipeline/execute_read_usage/v1`
- Example-local ABI: `example/tool_pipeline/async_atomic_tool/v1`

The adopted registration freezes the implementation revision, source-file and
handler hashes, input/output schemas and conversion/rounding policy. JSON never
contains an import path or a callable. Registration is a trusted HOST decision;
source hashes record that decision rather than sandboxing hostile Python.

The **existing** `invoke_registered_tool` checks the started execution, its allowed
tool key, adopted registration and exact identity/contracts on the owner thread.
A synchronous blocking tool at this boundary would serialize the owner. This
example therefore explicitly registers `async def` atomic tools. The checked
call returns a coroutine; the one-step executor verifies that type and awaits
it on the already admitted Harness worker. There is one await and one tool
operation per executor, followed by normal resource publication. It does not
create another thread pool, ready queue, completion map, event loop scheduler
for multiple business steps, or persistent ledger. The existing Harness worker
limit is the sole concurrency capacity.

This is an advanced, example-local trusted HOST ABI. It is not a new generic
async API in core, a managed-plugin subprocess receipt, or a managed-tool action
receipt. The evidence is the exact registered tool binding plus real business
operation admission/Start/input delivery/output/Success facts. A tool wrapper's
in-memory test observations are auxiliary evidence, never admission authority.

## Independent arithmetic and negative cases

[tools.py](tools.py) computes using `Decimal` with precision 50 and explicit
`ROUND_HALF_UP` for **each interval** to two decimal CNY places, then sums those
rounded amounts. The validator separately uses original integer Wh and
fen/kWh: `rounded_fen = (Wh * fen_per_kWh + 500) // 1000`. It never calls the
Decimal compute helper. It also checks source versions, original schemas,
interval coverage, boundaries, every normalized value, each amount and totals.

The rounding fixture has two 5 Wh intervals at 100 fen/kWh. Each half-fen rounds
to one fen, for **0.02 CNY**; rounding the aggregate would incorrectly give 0.01.

```bash
python -m examples.tool_pipeline.run \
  --usage examples/tool_pipeline/fixtures/usage-rounding.json \
  --tariff examples/tool_pipeline/fixtures/tariff-rounding.json \
  --run-dir /tmp/rpnh-tool-rounding-run \
  --output-dir /tmp/rpnh-tool-rounding-export
```

## Focused tests and transport limits

```bash
python -m pytest -q examples/tool_pipeline/tests
```

The default test path uses the genuine `OwnerEventLoop` AF_UNIX listener and
socketpair. The native CLI has **no automatic fallback**. If the platform denies
AF_UNIX, it reports BLOCKED/exit 2. Do not interpret that as a native runtime pass.

For semantic testing on such a platform, explicitly select the test-only pipe
transport:

```bash
python -m pytest -q examples/tool_pipeline/tests \
  --tool-pipeline-transport=pipe
```

[tests/pipe_transport.py](tests/pipe_transport.py) changes only socket creation,
wake FDs and cleanup. It inherits the actual owner's HOST submission, completion
watching and dispatch code. Registry, Harness, tool identity validation, tools,
schemas, publication, Success and terminal evaluation are unchanged. This does
**not** validate external socket clients, native IPC or plugin subprocesses.
Run the default suite and native CLI on a Linux/WSL2 host permitting AF_UNIX to
close that separate transport acceptance gap.

The tests use controlled events, not elapsed-time guesses: both read handlers
must have entered on separate workers while both exact Registry firings remain
active; usage normalization must settle while tariff read is still blocked;
join must remain disabled. Tests also cover capacity, causal resource refs,
missing-input admission, wrong tool identity, invalid units/time/values,
double rejection, schema-valid `1.71` candidate rejection, rounding, unresolved
worker failure, terminal replay without dispatch and read-only reconstruction.

## Boundaries

- This explicitly declared PN is **not** arbitrary Python-to-PN compilation.
- It is not an automatic lowering of `run_tool_program`, and does not implement
  a single parent tool's nested typed execution-net/result/failure bridge.
- Operations are local immutable-read/pure computation. There are no external
  writes, retries, payments, provider calls, Docker runs or new CI triggers.
  External-effect `outcome_unknown` handling is outside this example.
- Readback exports are observations, not an extra workflow authority. Exact
  versions are immutable through Registry APIs. Core currently verifies stored
  payload presence/size, not cryptographic resistance to same-length disk
  tampering; the storage directory is trusted. Artifact hashes are delivery
  checksums, not a new Registry integrity guarantee.
- Recovering arbitrary interrupted active tools is not added here. Unresolved
  firing states require the existing recovery/reconciliation rules. No
  `completed` dictionary or report file permits a restart to skip authority.
