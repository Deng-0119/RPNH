已实现的语义
两个分支分别 read → check → normalize，再进入 AND-join → Decimal compute → 独立 validate → publish；共 10 transitions、18 places。标准 fixture 应得到 2.000 kWh、1.20 + 0.50 = 1.70 CNY。每一步是现有 Harness 准入并结算的 operation，同一 Registry 记录精确资源版本、Start、输出和 Success。
HOST 显式注册受信 callable；example-local coroutine 由原先已 admitted 的 operation worker await。这不是 core 通用 async API、managed-plugin 子进程 receipt 或 managed-tool action receipt。read 消费已交付的 Registry artifact，没有外部 I/O，不应报告 I/O 加速。两路原始快照为显式独立 products，不依赖隐式广播。

现有证据的边界
原生 CLI 在云端实际尝试后因 AF_UNIX PermissionError errno=1 阻断，退出码 2，没有自动 fallback。云端语义运行选择显式 test-only OS pipe，只替换 owner 的 wake transport；Registry、Harness、身份校验、发布和终态路径继续使用真实 core。该证据不能算作原生 OwnerEventLoop/socket 通过。最终分层结论与每次已执行命令见 VALIDATION_SUMMARY.txt 及 EVIDENCE_MANIFEST.json。任何未完成或旧版本结果均须保留其限制。

原生补验
以下命令在最终交付版本的 README、CLI 和 tests 中核对后提供。从仓库根运行，使用当前已验证 Python 解释器。运行与导出路径均放在仓库外且各次子目录必须不存在。不得设置 pipe 选项、注入 PipeOwnerEventLoop、monkeypatch socket 或另造 transport 后仍声称“原生”。

A. 定向默认测试
python -m pytest -q examples/tool_pipeline/tests

可使用 pytest 的 --basetemp 指向专用、全新且仓库外的目录，保留测试生成的运行/导出材料。不要指向已有业务数据；pytest 会管理并清理其 basetemp。记录 stdout、stderr、退出码、起止时间和完整测试列表；失败也必须保留。

B. 标准原生 CLI
python -m examples.tool_pipeline.run --run-dir <新的仓库外运行目录> --output-dir <新的仓库外导出目录>

应以 0 退出，打印 PASS/1.70，Registry terminal run_outcome=complete，10 个 firing，12 个业务中间及最终资源，actual_model_call_counts=[0,0]。结果必须来自终态资源，而非单看 report 文件存在或 JSON validated 标志。

C. 逐行舍入 fixture
python -m examples.tool_pipeline.run --usage examples/tool_pipeline/fixtures/usage-rounding.json --tariff examples/tool_pipeline/fixtures/tariff-rounding.json --run-dir <另一新运行目录> --output-dir <另一新导出目录>

两个区间各 0.01 CNY，总额 0.02 CNY。不得改成先求和后舍入的 0.01 CNY。

D. 进程重开与只读回读
结束生成原生标准运行的 Python 进程，把旧 export 移到保留证据目录（不要删除原始记录），让原来的 export 路径不存在；另起进程执行：
python -m examples.tool_pipeline.run --readback --run-dir <标准原生运行目录> --output-dir <全新回读导出目录>

核对最终报告、source/candidate/validation 精确 refs、全部 lineage、checkpoint、firing/events 与原导出一致；max Registry ordinal 不变、没有新 dispatch。回读仅使用 Registry 持久化材料，不可注入旧 Python 对象、export JSON 或 completed cache 来恢复业务流程。保留重开前后的比较记录。若 CLI 当前输出的字段集合有差异，区分重建稳定字段与仅运行期间附加的 stop_reason/transport 字段。

必须审查的验收点
1. 真实 overlap：controlled barrier 显示两个 read 工具函数体在不同 worker 均已进入且未退出，与 Registry 两个精确 active firing 对应。future 数量、coroutine 创建、wall-clock 变快均不能单独证明并行。
2. 分支进度和 AND-join：tariff read 仍被 barrier 阻塞时，usage read/check/normalize 已按真实 Success 落库；join 未 enabled、未 Start。两支 normalize 都 settle 后，join 才可 admission/Start。
3. 权威顺序：逐个 firing 核对 Registry admission、Start、output registration、Success/settled 的原始事件顺序，以及 read → check → normalize → join → compute → validate → publish 的偏序。所有产物的业务 parents、Registry derived_from、实际 claimed input refs 必须一致。
4. 独立 validator：验证器从原始整数 Wh 和 fen/kWh 重算 rounded_fen=(Wh*fen_per_kWh+500)//1000，不调用 Decimal compute helper；逐项、总额、单位、区间、source version 都必须检查。
5. 反例不 publish：错误单位、时间不匹配、负数/float/NaN/重复/重叠/越界输入、两路同时错误、schema-valid 1.71 候选、伪造 lineage 或错源版本，均不能生成 validated/final 或 publish_report Success。两路 rejection 应均可追溯。
6. 准入与权限：缺任一 join 输入不可启动；缺 validated 资源不能 publish；错误工具 identity/allowed-tool 被拒绝；同 Registry 的非 claimed sibling ref 不构成读权限。
7. 异常与恢复：未预期工具异常保留未决 firing，重建 Harness 不自动重放；已经 terminal 的 Registry 重建不重复 dispatch。不得将 reconciliation_required 写作成功。
8. 容量：验证 max_in_flight=2 时最多两个 active；如最终现有测试包含单 worker 容量检查，也按默认原生路径运行。不要添加自建调度器。
9. 0 真实模型：用 Registry actual_model_call_counts 支持结论，同时确认没有调用 provider、Docker、Actions 或外部业务 API。
10. 不扩大结论：不声称任意 Python 自动转 PN、不声称 run_tool_program 已自动 lower、不声称原生 plugin receipts、不可宣称防同长度磁盘篡改或通用任意中断恢复。

现有 tests 是首选证据入口。若某项验收尚无完整原始记录，可补最小、明确标注 test-only 的原生 probe，保持注册与 Registry 路径不变，并随结果交付 probe 源码；不要改写业务实现来使断言通过。云端独立 probe 中可能有旧实现缺陷发现记录，是否仍适用以分层 manifest 与最终同版本复验为准。
