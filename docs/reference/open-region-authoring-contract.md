# Open-region authoring contract

## Status as of 2026-10-06

The static draft and historical NOT_RUN matrix below are preserved as proposal
history, not a current implementation wait. Integrated bounded author contracts
are described by [open-region authoring](open-region-authoring.md) and
[descendants](open-region-descendants.md). The full 48-row/185-variant matrix
was not rerun and is not relabelled PASS. See [finite validation](../guides/release-validation.md)
for current integration acceptance and limits. References below to a next
authorization stage or pre-coding approval belong to the original draft date.


This freezes a **DRAFT proposal for independent review, not an approved protocol or an implementation**. All names newly defined below are proposed. The accompanying [acceptance matrix](open-region-acceptance-matrix.json) is entirely NOT_RUN. No production schema, class, import, test, execution, adoption or external action is added by this document.

## 1. Fixed direction and first usable path

The already selected author policy is explicit `lineage_mode="new_lineage"`, with no omitted/default mode. Extracting a selection is provenance, never full-parent or merge history. Persist an independently readable, genuinely nonterminal O; a separate strong command closes its exact selection using caller-specified context and completion. A prospective target remains pending until an actual Assembly proves the match. Structural closure grants no input, lease, capacity, effect permission, readiness or runtime adoption.

Minimum real path: publish closed S containing A→B→C and an explicitly declared C terminal; select only B; publish and reopen open O with ingress A→B, egress B→C and missing-completion obligations; caller explicitly selects C and its terminal and supplies the ingress policy; reconstruct B+C with `extract_module(S, ExtractPlan(kind="components", components=(B,C), boundary_policy="preserve_all_dependencies", output_name=...))`; compile and publish strong closed D; an actual new Assembly/v4 publishes and fully consumes D at its exact planned member. A full Registry read after reopening must traverse these resources. A fabricated terminal, a counter, a standalone helper assertion or an unconsumed adaptation document does not meet this gate.

The initial reconstruction adapter is `rpnh/collaboration/source_component_completion/v1`: whole basic `operation` components from one exact ordinary closed Module/v1 source. It preserves the selected and context component declarations and internal links byte-for-byte as canonical JSON; only the existing extractor's public-boundary/name projection is permitted. The caller selects the union explicitly; reachability does not select C. Source-wide requirements/budgets retained by the existing extractor remain retained and checked. Unsupported graph internals, opaque author constraints, arbitrary PN/node selections and richer adaptations are reported as missing capabilities, not reinterpreted as ordinary components or permanently excluded product goals.

## 2. Authority, history and references

S, O and D have distinct logical identities. O and D both have `parent_revision_refs=[]` and `selected_change_refs=[]`. Their source relationships use the new provenance resources below. O's `definition_kind` is `open_region`; D's is `closed_module` and D's `open_region_contract_ref` is null. No unfinished obligation is hidden in D's NetRevision descriptor.

O can head a Branch/v1. D starts its own closed Branch with fork base D and no upstream-Branch claim to O. Advancing O's Branch to D fails even with correct version/head/stream expectations: D is not O's direct descendant. Existing upstream fork semantics require head=fork base and cannot express extraction. A genuine closed successor E can advance D's Branch. Branch publication checks author-head history, not material proof or target eligibility.

All refs use the existing source-qualified exact version/resource wire. The first publisher and full reader use one bound local source and the exact registered owner task version; a same-shaped ref from another source/owner is not an alias. Source binding, bootstrap authority, producer authority, exact schema authorities, canonical publication/producer relations and object-store bytes are verified in one read cut. Names, paths, Branch heads and “latest” cannot select evidence.

Element identity remains lineage-qualified. O and D allocate new IDs; cross-lineage origin rows carry exact source revision+element IDs. Existing `author_element_map/v1.copied_from` remains parent-only and is not repurposed for S/O origins. Retention in E keeps same-kind IDs; copy creates new IDs. Equal payload bytes create neither ancestry nor membership.

## 3. Exact proposed record family

Every record has its listed `schema_version`, all listed fields, no unknown fields, canonical data-only JSON and explicit nulls where allowed. Lists named sets are sorted/unique by canonical identity; declaration arrays preserve the source's semantic order. “Pin” means `{resource_ref, schema, schema_authority_ref, payload_bytes, payload_sha256}`. Actual stored payload bytes must equal canonical JSON, not merely parse to an equal object. Protected schema authority uses its exact frozen catalog; application schema authority uses its exact schema resource, with exact supported schema content and a digest of its actual bytes. Refs/pins are validated, not trusted because their hashes are present.

An inventory item is `{item_id,kind,source_locations,selected_element_ids,outside_element_ids,contract,extraction_disposition}`. Each location is `{revision_ref,material_role,json_pointer,element_id}` with explicit null element ID where only compiled evidence exists. `contract` is `{facts,unknowns}`: each fact is `{semantic_key,value,source_locations}`; semantic keys are `schema`, `direction`, `cardinality`, `order`, `generation`, `outcome`, `completion`, `arbitration`, `resource`, `effect`. Actual declaration values are retained; unknown keys are listed, never invented. Item IDs are `boundary:` plus UUIDv5(namespace URL, canonical `{contract:"open_region_boundary_identity/v1",source_revision_ref,selection,kind,source_locations}`); duplicate IDs/locations with conflicting facts fail. `extraction_disposition` is exactly `internal|boundary|outer_owned|needs_adapter|unrepresentable`.

An adaptation disposition is `{item_id,status,adapter,output_element_ids,evidence,remaining_requirements}` with status `direct|adapted|needs_adapter|incompatible`; evidence is `{source_locations,output_locations,request_fields}` using exact source locations, result material-role/JSON-pointer pairs and closure-request JSON pointers. `adapter` is null only for a directly preserved relation. In the first adapter, supported dispositions are: source-internal preservation; selected→context link made internal; caller-authorized incoming link projected to a public entry; explicitly selected declared C primary/alternatives supplying completion. Every item is accounted for exactly once, and every context-created crossing is inventoried too. Unknown coverage, missing completion, unexplained cardinality, incompatible carrier, resource arbitration, effect responsibility or return semantics block closed publication. Known unsupported boundaries can remain saved in O.

`remaining_requirements` can contain live input availability or future runtime handle/claim/adoption requirements whose *structural contracts* are complete. It cannot hide missing structural arbitration or business completion meaning. An outer-owned lease without a proved usable structural protocol is `needs_adapter`, not “closed but pending runtime”. Actual source lowering and compilation must agree with the inventory; inspecting only named Module links is insufficient.

## 4. Complete commands, identities and publication

Proposed command schemas are `open_region_author_command/v1` and `open_region_closure_author_command/v1`. Both contain exactly: `schema_version`, `algorithm`, `source_id`, `owner_task_ref`, `producer_principal_ref`, `command_id`, `request`, `schema_authorities`, `schema_authority_sha256`, `result_revision_ref`, `parent_revision_refs`, `selected_change_refs`, `prepared_materials`.

The open request contains exact source/provenance selection and required `lineage_mode`; the closure request contains exact `open_revision_ref`, exact provenance ref, caller-selected context/completion, complete extract plan, all explicit dispositions and exact prospective intent. The prepared-material set is exact: open = provenance, definition, open element map, inventory, open HOST requirements, open contract; closure = intent, origin map, adaptation, Module, ordinary element map, ordinary boundary map, ordinary HOST requirements. Each entry is `{role,schema,resource_ref,document,metadata,payload_bytes,payload_sha256}`. O's descriptor links the six appropriate resources; D's ordinary four material refs point to its result. Closure command directly fixes every input and output, including adaptation and origins.

New definitions dispatch through exactly one marker: `open_region_author_command_v1` or `open_region_closure_author_command_v1`; its value is the canonical source-qualified command resource ref. Every command-owned material has its exact command marker; the command's own descriptor identifies the schema, not a recursively read command. Marker discovery remains narrow and rejects unknown/dual `_author_command_` markers. Source/command/material refs may cross-reference fixed identities, but validation follows a typed dependency path and never recursively reads a command's own prepared-material back-reference as a new parent.

Proposed deterministic identity rule: `key = protocol_prefix + canonical_text({command_id})`, using distinct prefixes `collaboration-open-region:` and `collaboration-open-region-closure:`. For kind `resource` or `resource_version`, use the existing TypedId/UUIDv5 namespace-URL rule over canonical `{scope:key,task:owner_task_logical_id,source:source_id,kind}`. O and D are roots; neither reuses S's logical ID. Resource identities use the existing bootstrap-scoped `_material_ref` rule with `key+":"+role`. IDs do not hash mutable payloads; same command/different content conflicts. New element IDs are `element:` plus UUIDv5(namespace URL, canonical `{contract:"open_region_element_identity/v1",lineage:result_logical_id,kind,origin}`), where origin is the exact source-element tuple for selected/context elements or the exact output locator plus ordered source IDs for projections. The full reader recomputes these rules.

Prepare checks before writing; immutable command/material prefixes may survive interruptions. Before final revision publication, revalidate all exact dependencies and output material in the final cut. Immutable revision commit is a separate outcome from Branch creation and Assembly commit. Same command/content returns the exact existing full-validated result with zero writes; same command with any changed request, owner/producer, context, intent, schema authority or output conflicts. A retry after a rejected final cut resumes the same immutable prefix once its original inputs are available; it cannot overwrite or reinterpret it. Writer-epoch checks and existing canonical transaction/publication validation remain mandatory.

## 5. Consumer chain and Assembly/v4

1. The descriptor reader returns only NetRevision structure. The new full open reader validates source, command, O projection, inventory, exact requirements and all open obligations in one snapshot; it never compiles O as a Module.
2. The ordinary full closed entry `validate_closed_revision` dispatches D's exact new marker to its strong closure consumer. That consumer fully reads O and S, validates caller choices, reconstructs with the actual existing extractor, recompiles with exact Registration/HOST declarations, and compares the complete command, result refs, bytes, maps, origins and all dispositions. O still fails every closed entry; it is provenance, not closed ancestry. The result exposes `adaptation_claim=exact_current_result`, `target_status=prospective_unverified`, exact command/adaptation/intent refs. No subclass-only test may silently erase these facts.
3. New opt-in Assembly/v4 uses new descriptor/plan/command/lowering schemas and an exact recipe `direct_adapted_member_resolver/v1`. The first implementation supports direct ordinary closed-v1 members (including accepted plain merge proofs through their existing full readers) and direct `adapted_result_current` members. The §6 ordinary-new-definition conversion and its positive E/copy/merge-v2 consumers are a following bounded milestone, not prerequisites for this first loop. Graph and child Assembly membership remain available through accepted v2/v3 contracts; v4 does not silently claim to extend them. Its own history is v4-only. Its member row adds explicit `claim`, exact `adaptation_ref`/`intent_ref` or null, and exact locked material resolution. There is no fallback from failed adapted resolution to an ordinary claim.
4. Assembly producer and full reader derive the target from their own actual source binding, exact owner, command, v4 recipe, exact parent selector, member ID, D ref and proof refs. They independently compare every intent field. They validate actual ingress public exposure or the exact promised other member+revision+exit connection, all result boundaries, selected root completion, carrier uniqueness/fusion and current-context HOST lowering. An intent does not prescribe an already registered Assembly. Before commit it remains prospective; a successful Assembly proof returns the exact matched member resolution. The intent resource is never mutated into a membership fact.
5. v4 reconstructs its entire final Module and actual-fragment lowering/origin map and retains strict paired generated checks: **exact ordinary `ValidatedClosedRevision` type**, deterministic generated command/ref, exact owner/producer, generated-parent chain, four material refs/documents and actual compilation. A merge/adapted subclass is not a generated substitute. Parent/member/generated dependencies use the same snapshot and active path; sibling reuse is not a cycle. Final publication revalidates the same dependencies.

Concrete v4 wire: descriptor fields are the accepted v2/v3 field set (`revision_ref,owner_task_ref,producer_principal_ref,command_id,parent_revision_ref,plan_ref,generated_revision_ref,compiled_inventory_ref,lowering_mapping_ref`) under `registry_v1/collaboration_assembly_revision/v4`. Plan/v4 retains the exact v2 plan field set and material-lock/signature fields, with member rows `{member_id,display_name,revision_ref,claim,adaptation_ref,intent_ref,resolution}`. First-loop claims are exactly `plain_closed_v1|adapted_result_current`; resolution is `{proof_kind,command_ref,definition_ref,element_mapping_ref,boundary_mapping_ref,host_requirements_ref,historical_origin_refs}`. Ordinary legacy command text is already carried by its material marker, so `command_ref=null` is explicit for that proof kind. Adapted rows require both proof refs; others require both null. Connections and completion retain exact element IDs. Recipe fixes `history="same_version_logical_history/v1"`, `containment="direct_members/v1"`, `instance_identity="exact_direct_member/v1"`, stable member UUID scoping, explicit `shared_exact`, selected primary with alternatives, actual final-context fragments, remove-only-Assembly-connections carrier cut and canonical JSON byte locks. The full v4 recipe has no unknown keys or optional fallback. Command/v4 fixes the complete plan and generated materials using the existing Assembly complete-envelope pattern, a new v4 marker/prefix and deterministic same-version result/generated IDs. Lowering-map/v4 retains complete actual-fragment origins and additionally pins each member claim and its exact proof refs; it records validated target matches. This is not a new mutable runtime topology.

**Generated-v1 authority decision.** Keep the accepted boundary: Assembly owns composition and member-origin proof; its generated G has its independent ordinary closed-v1 contract. A bare `validate_closed_revision(G)` proves only G. It neither claims nor verifies the Assembly's adapted-member match. Consumers requesting composition/adaptation proof must pass the explicit Assembly/v4 ref and use its full entry. No mandatory G→Assembly strong proof back-link is added; that would create needless proof cycles and silently strengthen the accepted ordinary-v1 promise. Conversely, presenting G as evidence of D's original source/target or bypassing an API that requires Assembly proof fails that API's typed claim requirement. Intent and claim checks are not a data-loss-prevention label that follows arbitrary reauthored bytes.

Reusing the source O for targets m1 and m2 requires distinct exact target adaptations D1/D2, even when their Module bytes match. The first positive reuse case puts D1 and D2 in separate valid Assemblies, each selecting its own adapted member as root completion. In one Assembly, the present `member_primary_terminal` expectation cannot be true for two different adapted members because root completion selects one member. Reject that unmatched target; a positive same-Assembly multi-adapted case awaits an explicit alternative/contribution-completion contract. This is a semantic capability gap, not an arbitrary global member-count cap; any supported number of ordinary members remains governed by the real composition rules. A later Assembly command or parent selector is a new target; rerun explicit closure against O with a fresh intent, producing D2 as another closed root. This first contract has no wildcard targets or reusable retarget-attestation. Nested adapted placement requires a future full occurrence-path contract and is explicitly unsupported by this resolver. It is not a permanent nesting cap.

## 6. Ordinary E, merge and copy: explicit claims

The following engineering recommendation is **DRAFT_REVIEW_REQUIRED / NEXT_EXTENSION**. Its positive E/copy/merge-v2 implementation is not a prerequisite for the first S→O→D→Assembly loop. The first loop must fail closed at both legacy producer and legacy full-reader entries: a `closed_author_command_v1` revision E whose parent is the new proof-bearing D (or whose validated ancestry requires an unsupported new claim) is rejected, even if E otherwise has canonical ordinary material. `ClosedModuleAuthor.publish` and `materials._validate_materials_at` must both enforce the boundary; checking only the public publisher leaves a read-side downgrade. Legacy Assembly/merge entries also reject D. None may silently return/classify such E as a claim-free base `ValidatedClosedRevision`. No positive derived/merge-v2 fixture or new family implementation is required to exercise this canonical old-marker rejection.

The later explicit conversion prevents old current-result claims from becoming accidental edit/merge authority without turning history into a permanent dead end. Adding `ordinary_new_definition` to an Assembly member recipe requires its own explicit later resolver-contract version; it is absent from the first `direct_adapted_member_resolver/v1` recipe and cannot silently expand that recipe.

## 7. Failure dispositions and compatibility

Failure results identify exact ref/item/field and phase. Required classes are `unsupported_contract` (unknown recipe/version or absent adapter), `invalid_selection`, `unresolved_boundary` (saveable O, no closed candidate), `incompatible_boundary`, `missing_exact_material`, `authority_mismatch`, `material_integrity_mismatch`, `command_conflict`, `stale_writer_or_branch`, `proof_cycle`, `target_mismatch` and `claim_not_proved`. Missing/unknown is never empty, closed, current or authorized. Error names are proposed semantic categories, not claims about existing exception spelling.

The explicit new catalog composes accepted schemas only after exact schema/type equality checks; accepted builder inventories, schema/recipe bytes and v1/v2/v3 promises stay unchanged. Newly proof-bearing D/E/copy/merge-v2 must be explicitly rejected by legacy Assembly and merge eligibility gates; current `isinstance(ValidatedClosedRevision)` is insufficient. Newly introduced marker dispatch in the shared full reader does not enlarge those older resolver contracts. Accepted ordinary/graph/merge-v1/Assembly-v2/v3 inputs and strict generated pair checks keep their accepted behavior. An ordinary G can still be consumed under its own v1 contract; that does not become composition proof.

An unsupported graph/node adapter, unrelated lineage transformation, cross-owner protocol, richer feedback/lease/pool/slot/reset/effect disposition, reusable target binding or deeper adapted occurrence remains a tracked capability gap in the total plan. No arbitrary product cap is introduced. Unknown business outcomes, cancellation or continuing interaction cannot be converted to successful completion. No runtime, provider, model, network, browser, worker execution, new run, effect, remote/PR/Actions/security change or 14C work belongs to this slice.
