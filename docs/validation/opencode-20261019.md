# OpenCode 1.19.3 validation — 2026-10-19

[中文](opencode-20261019_ZH.md) · [Operator guide](../guides/opencode.md)

## Version and scope

The target is [opencode-ai 1.19.3](https://www.npmjs.com/package/opencode-ai/v/1.19.3),
obtained with `npm install --prefix <task-install> --no-audit --no-fund opencode-ai@1.19.3`.
The task's version discovery checked npm `latest` and the
[GitHub stable release v1.19.3](https://github.com/anomalyco/opencode/releases/tag/v1.19.3).
The tag resolves to `e3c4eb242585dcd77be1a867391b7c25fd47ce52`.
The actual Linux x64 ELF probe returned exactly `1.19.3`, exit 0, empty stderr.
The npm `.bin/opencode` entry resolves to `opencode-ai/bin/opencode.exe`, an
internal hard link to the tested `opencode-linux-x64/bin/opencode` ELF. The
production launcher's isolated exact-version probe also passed via that PATH entry.
No global installation, login or account configuration was changed.

The RPNH starting point was public `32b566da0a8c6249b1e42c0c23896b6c94753483`,
with the local changes described here. Native execution used Ubuntu 24.04.4,
WSL2 Linux 6.6.87.2, x86_64, glibc 2.39, a 36×120 PTY and `xterm-256color`.
Only 1.19.3 is currently accepted. Earlier 1.18.32/1.18.35 results remain
historical; development 2.0.32 and other versions are not certified by this work.

## Protocol changes

The stable client now bootstraps both legacy session APIs and a location-scoped
catalog. Source references at the release commit include generated
[SDK types](https://github.com/anomalyco/opencode/blob/e3c4eb242585dcd77be1a867391b7c25fd47ce52/packages/sdk/js/src/v2/gen/types.gen.ts),
[TUI DataProvider](https://github.com/anomalyco/opencode/blob/e3c4eb242585dcd77be1a867391b7c25fd47ce52/packages/tui/src/context/data.tsx),
[sync bootstrap](https://github.com/anomalyco/opencode/blob/e3c4eb242585dcd77be1a867391b7c25fd47ce52/packages/tui/src/context/sync.tsx),
and [attach](https://github.com/anomalyco/opencode/blob/e3c4eb242585dcd77be1a867391b7c25fd47ce52/packages/opencode/src/cli/cmd/attach.ts).

- `/experimental/console` returns no managed providers or switchable organizations.
- `/api/location`, `/api/agent`, `/api/model`, `/api/provider` and `/api/command`
  project the existing RPNH display directory, agent, exact profiles and controls.
- `/api/integration`, `/api/skill` and `/api/reference` return empty catalog envelopes.
- SDK deep-object `location[directory]`/`location[workspace]` queries remain scoped
  to the isolated display directory. Other workspaces and ambiguous queries fail.
- New API writes and native credential/tool/session effects remain unsupported.
  No provider endpoint, key, request override or parallel Registry is exposed.

The packaged compatibility schema records the current source-extracted subset;
it is not generated by the upstream SDK or a claim of full v2 API support.
The legacy 1.18.35 candidate is removed from the accepted profile set. No version
range, environment override or fabricated version response replaces adaptation.

## Failures retained and corrections

1. The original strict 1.18.32 probe rejected the real 1.19.3 client, as expected.
2. The first native fixture setup was blocked by missing scipy. Scipy 1.18.1 was
   installed only in the task dependency directory; the existing environment was
   not modified, and the affected check was rerun.
3. After the Console response was added, the real client still requested
   `/api/agent` and `/api/integration`, which returned 404. A diagnostic retry
   identified these paths; inspecting the stable DataProvider established all
   eight required catalog reads. The implementation now supplies their actual DTOs.
4. The first Registry native window reached the correct PN payload, but its old
   terminal assertion timed out waiting for a heading above the long PN viewport.
   The test now observes the rendered `Rpnh-Observation` role while retaining the
   full PN structural comparison. The corrected window passed.

Original failures, terminal excerpts, route records and later successful windows
remain in task-local evidence. No task-side hashing, source-tree gate or whole-byte
replacement audit was run. Git revision/worktree context is descriptive only.

## Reproduction and limits

The [guide](../guides/opencode.md#explicit-native-offline-checks) gives the two
explicit native commands and current regression selection. The test helper does
not install dependencies or accept a user Registry path. Use a writable test
root for `TMPDIR` and pytest `--basetemp`; disable pytest caching when source-tree
writes are unwanted. Preserve the task-local client if it supplies the active PATH.

This is limited offline WSL2 acceptance. No real provider/model or external tool
effect was invoked. Native picker/effort matrices, forced SSE reconnect,
long-history pagination, active-worker recovery, non-WSL Linux, Windows, macOS,
mini mode, upstream plugins/tools and development 2.0.32 were not validated.
No OS network sandbox or new wheel validation is claimed. Terminal checks are
bounded text observations, not screenshots. Usage/cost/context remain unavailable.
